# Blocking regression: partition direct read and memory exhaustion

Status: root cause identified and corrected in the prototype. Bounded read and write validation passed after the correction. The fix still needs a dedicated test-kernel boot before it can be proposed as a generic kernel change.

The previous 15-minute test passed aligned mmap/O_DIRECT reads, reset and three orderly removal cycles. A subsequent direct read of the EFI partition using GNU dd (bs=1M, iflag=direct) stalled before producing its first output block. The intended backup file remained zero bytes and is not a backup. Filesystem probing and a read-only EFI mount/unmount had previously succeeded; partition 1 is FAT32 and partition 2 is APFS.

The dd process blocked in submit_bio_wait / __blkdev_direct_IO_simple. Teardown phase 1 then blocked in blk_mq_freeze_queue_wait during nvme_ns_remove. No further teardown phases, forced module removal or tunnel shutdown were attempted.

The ThinkPad netconsole log captured repeated swiotlb_dyn_alloc allocation failures, order 10 on a 16-KiB-page kernel (16 MiB), at 22:02:31 UTC and later. Global OOM kills started at 22:04:45 UTC, eventually killing desktop and system services. SSH became unavailable. This was a real I/O and memory failure, not merely a black-screen/HDMI issue. There were 7,543 DART-selection messages, 63 visible dynamic-SWIOTLB allocation warnings and 122 OOM victims in the captured interval.

The synthetic external PCIe root omitted the `dma-coherent` property that is present on the native Apple PCIe root. Consequently Linux treated the NVMe device as non-coherent. The dma-iommu scatter/gather path can then bounce an entire request through SWIOTLB when an element is not safe for non-coherent DMA. The aligned custom reader avoided that path, while the general direct-I/O request exercised it. With the request stalled, dynamic 16 MiB pools kept being requested until usable memory was exhausted.

Adding `dma-coherent` to the synthetic PCIe root changed the endpoint diagnostic from `coherent=0` to `coherent=1` without changing its IOMMU group, SID, 32-bit DMA mask or DART aperture (`0x80000000..0xffefffff`, 16 KiB granule). The following checks then passed with SWIOTLB used/transient/high-water counters all remaining zero:

- 64 KiB direct read;
- one 1 MiB direct read, matching the failing buffer shape;
- full 200 MiB direct read of the EFI partition in 217 ms, SHA-256 `6e19ddabb421d7855d24d79338bb87eb4259eac6f674b5bace8c453e44f0bb62`;
- verified 200 MiB pre-write image with the same SHA-256;
- create, fsync, unmount, read-back and delete of a 4 MiB FAT test file;
- clean read-only FAT check after deletion;
- staged NVMe/PCIe teardown, tunnel deauthorization and module unload.

The write test grew the FAT root directory by one cluster; the temporary file was removed and existing files were not modified. The exact pre-write image remains on the test Mac for recovery.

Recovery required one Ubuntu reboot. Prototype modules are not loaded automatically. No new kernel has been installed. The first source build of 7.2.12-usb4-test1 was terminated during the OOM event and can be resumed incrementally.
