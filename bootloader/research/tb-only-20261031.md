# Probe40: TB3 with the native USB controller held in reset

The current regular Ubuntu kernel (7.2.0-1001-asahi-arm) recognizes the
unchanged Yottamaster as Intel Ash Creek, generation 3, two 20 Gb/s lanes.
Its journal reaches Phase2 at 4.493 s, Phase3 at 4.511 s and Connected at
4.514 s (message-consumption timestamps). The firmware version and cable
parameter 0x413 match Probe39. This establishes working router discovery,
not external NVMe support in the regular kernel.

A guarded read-only snapshot, using the existing fixed PHY register
allowlist and checking power domains before every read, matches all ten
core PHY controls. Three of seven PIPE controls differ: offset 0 is 0 vs 5,
offset 4 is 0x16 vs 0x10, and offset 0x1c is 0x10 vs 1 (Linux vs Probe39).
PIPE AON bit 0 is DWC3_RESET_N and bit 4 is DWC3_FORCE_CLAMP_EN.
Linux therefore has DWC3 held in reset while the TB3 link is connected.
These are steady-state snapshots, not proof of the startup sequence.

Linux tipd/core.c:cd321x_update initializes new_role to USB_ROLE_NONE and
only selects a USB role when data-status bits 4 or 5 indicate USB2/USB3.
Probe39's CD321x data 0x06010003 has neither bit. Our earlier hostrun
experiment nevertheless released DWC3, configured its PIPE and ran xHCI.
The earlier extracted PHY comparison assembled a host-role call sequence;
it did not validate whether that sequence should be selected for this cable.

Probe40 adds an explicit tbonly diagnostic, rejecting non-TBT and native
USB connection bits before hardware mutation. It keeps the original
selected-controller stop/HALTED check, PHY calibration, ACIO and bounded
NHI control transactions. It leaves DWC3 reset/clamp asserted, does not
select USB2 host role, does not call the late PIPE callback, and performs
no DWC3 MMIO snapshot after reset is asserted. No xHCI rings or USB DMA
are started. A defensive library guard rejects this policy for USB4;
PIPE activation is forbidden for a hold-reset configuration. Existing
host/hostrun diagnostics retain their prior behavior.

No raw steady-state PIPE values are copied into hardware. The diagnostic
omits the inappropriate USB host calls, following the source-level
branch, and records the resulting PHY controls. This remains a hypothesis:
there is no hardware result yet. It does not claim universal TB/USB4 boot.

The independent return-path audit found that Probe39 completed and issued
reset. A later Ubuntu boot reached graphical.target before a forced power
button shutdown. Black HDMI therefore does not prove a failed guest boot.
The installed boot hash and empty GRUB next_entry were verified after
recovery. The RTKit diagnostic still requests SLEEP and retains powered
state until full reset, unlike Linux's poweroff teardown. That is an
explicit remaining cleanup difference; it is not changed together with
this link experiment and is not established as the black-screen cause.

phy/apple/atc.c at audited downstream HEAD
517fe27a2ce7fa8d03aa6705a10ff4422197ff5d. The currently running stock Linux
binary is a different build; source/binary equivalence is not asserted.
Original Asahi author credits are retained. No Apple disassembly used.

Validation required before arming: M1 build, sandbox tests including both
orientations/three inherited reset states and fault injection at every
core IO position, patch reconstruction, unchanged M1 configuration and
frozen payload hashes. RAM only, no permanent boot changes, external
PCIe tunnel or SSD IO. No repetition requested after a conclusive pass.
